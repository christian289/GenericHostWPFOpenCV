## 실제 C# ↔ Python 파이프 실행

`OhMyRudolph.PipeSmoke`가 실제 C# 클라이언트·프로젝트 Python·MediaPipe·Windows Named Pipe를 실행했습니다. 입력은 자체 생성한 **320×240 BGR 검은 Mat**, 미러 없음·회전 0도입니다.

- 정상 시작/요청/종료 3세션 × 12요청 = 36요청. 모두 얼굴 없음과 식별 정보 일치를 확인했습니다.
- 실제 Python 수신부에 잘못된 길이 0·음수·8MiB 초과, EOF로 잘린 헤더·본문, 연결을 유지한 2바이트 헤더 시간초과를 보낸 뒤 재연결·정상 요청을 확인했습니다.
- 이 실행이 띄운 정확한 소유 PID만 종료한 뒤, 죽은 파이프에 중간 I/O 없이 Start → Connect → 요청을 수행하여 재시작을 확인했습니다. 다른 Python 프로세스를 열거하여 종료하지 않습니다.
- 마지막 실행의 총 경과는 **11.52초**입니다. 이는 정상·오류 주입·재시작을 포함합니다.
- 36개 정상 요청의 왕복 p50 **2.93ms**, p95 **8.46ms**입니다. 카메라 프레임 지연·실제 얼굴 검출 성능·1920×1080 처리 성능을 측정한 값이 아닙니다.
- C# 프로세스 private bytes는 시작 **15,593,472**, 종료 **27,860,992**였습니다. 시작/JIT/초기화가 포함된 단일 짧은 실행으로, 정상 상태 메모리·장기 누수·Python 전체 메모리를 검증한 수치가 아닙니다.

## 실패 전·수정 후 근거

| 문제 | 관찰·수정·확인 |
| --- | --- |
| Python 수신 시간초과 | 설치된 pywin32에 CancelIoEx가 없고 CancelIo가 있음을 실제 확인. 2바이트 헤더를 유지하면 수정 전 실제 서버 재연결이 TimeoutException으로 실패(종료 82). CancelIo 후 overlapped 완료 회수로 수정한 뒤 같은 경로 통과 |
| 자식 종료 후 파이프 세대 | 실제 소유 PID 종료 후 재시작 요청이 EndOfStreamException으로 실패(종료 82). Windows venv 실행 PID와 실제 Python PID/부모 PID가 다름을 관찰. 새 Python 시작마다 새 pipe 이름을 사용해 종료 중인 이전 인스턴스로 연결되지 않게 한 뒤 같은 경로 통과. EOF를 성공으로 숨기거나 자동 재시도로 덮지 않음 |
| 폐기 중 연결·시작 경합 | 정적 리뷰로 발견. 폐기 시작 상태를 먼저 확정하고 완료 Task를 공유하도록 수정. 대기 중 연결 거부·동시 폐기 회귀를 포함한 최종 xUnit 통과. 수정 전 실행 재현 증거는 없음 |
| 오래된 프레임 확정 | 정적 리뷰로 발견. Running·현재 세션/세대·원본 캡처 후 1초 이내 조건을 검사. 정상/정확히 1초/초과 1tick/읽기 실패/오래된 세대/추론·큐 지연 등 BCL 판정 11사례 통과. 수정 전 실제 카메라 재현 및 수정 후 실카메라 확인은 없음 |

위 두 실행 실패는 개선 과정의 회귀 시나리오입니다. 원래 사용자가 관찰한 간헐적 통신 장애를 이 원인 하나로 설명하지 않습니다.

## 승인된 실제 UI 관찰

최종 실행 명령: `node scripts/dev.mjs ui-smoke --approved-no-camera`. 시작 화면 → 포토부스 → 라이트/다크 프레임 선택 및 `선택됨`/`선택 안 됨` 상태 → 뒤로 → 정상 닫기·종료 코드 0을 한 실행에서 확인했습니다. 카메라 미리보기 시작 버튼은 누르지 않았습니다.

같은 앱 소스의 별도 관찰 실행에서는 `--observe`로 프레임 선택 단계에서 대기한 뒤, native window screenshot/접근성 트리로 실제 배치를 관찰했습니다. 도구가 보고한 앱 창 캡처 크기는 2527×1428입니다. 카메라 꺼짐 상태, 0/4컷, 선택된 라이트 프레임과 시작 버튼을 확인했고 앱 창만 `artifacts/ui-smoke.png`에 저장했습니다. 바탕화면 전체·다른 앱·사용자 사진을 캡처하지 않았습니다. 화면 캡처는 Git 제외이며 최종 정상 닫기 실행과는 별도 관찰 증거입니다.

초기 UI 검증 두 번은 화면 선택까지 통과했으나 검증 도구의 종료 정보 조회에서 실패했습니다. 첫 번째는 attach-only Process의 ExitCode 조회, 두 번째는 FlaUI와 공유한 Process 객체의 연결 해제였습니다. [FlaUI 5.0.0 소스](https://github.com/FlaUI/FlaUI/blob/v5.0.0/src/FlaUI.Core/Application.cs)의 GetMainWindow 대기 경로가 자체 Process wrapper를 Dispose/교체하는 것을 확인하고, 직접 시작한 원본 Process와 `Application.Attach(process.Id)`의 별도 wrapper를 분리했습니다. 어서션을 제거하거나 종료 코드를 성공으로 대체하지 않았으며 수정 뒤 최종 실행이 통과했습니다. 이 두 실패를 앱 결함이나 실촬영 검증 결과로 계산하지 않습니다.


## 남은 제약·공개 경계

- 실행 직전 승인받은 카메라 없는 WPF/FlaUI UIA3 범위는 통과했습니다. 그 밖의 실물 UI 조작과 실카메라 검증은 실행하지 않았습니다. 기본 verify는 UI를 열거나 카메라를 켜지 않습니다.
- 실카메라·사용자 사진 저장·프린터·외부 공유는 실행하지 않았습니다. 프린터/외부 공유는 제품 기능도 아닙니다.
- DirectShow가 영구 정지하면 native Read를 안전하게 강제 중단할 수 없습니다. 3초 중지 제한 뒤 읽기 완료 시 해제를 연기하며, 오래된 프레임은 새 촬영으로 확정하지 않습니다.
- 짧은 합성 실행만으로 장시간 운영·여러 카메라/드라이버·장기 메모리 안정성을 보장하지 않습니다.
- 기존 정적 PhotoView/FastAPI 기능의 회귀·미확인 그림 자산 권리·설치 프로그램·깨끗한 PC 설치·배포는 확인하지 않았습니다.
- 로컬 변경은 전용 기능 브랜치 `feat/ohmyrudolph-podman-velopack`에서 검증 단위로 커밋 관리합니다. 원격 push·공개는 하지 않았으며, 공개 전 정확한 diff·권리·비공개 자료 검토와 소유자 승인이 필요합니다.
